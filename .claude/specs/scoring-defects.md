## Premises the tree contradicted

1. "The bimodality metric's scale changed" - it never changed since the first commit; the metric's mathematical maximum (2.0) sits below the threshold (2.5) and the metric points the wrong way (silhouettes score -4.0, smooth broad histograms +1.3). The penalty is removed, not re-thresholded.
2. "Three concert modifiers are dead" - `iso_tolerance_multiplier` is also on `sports` (0.3): 9 keys, 10 instances (`default.json` L205-207, L951).
3. "Fold quality inside `ScoringConfig.get_weights`" - five other consumers read `get_weights` and treat `quality` as its own weight (`comparison.py:872,1518`, `critique.py:223`, `percentile_normalizer.py:614-675,856,1791`). The fold is scorer-local.
4. "Skip NULL metrics in `build_metric_vector`" - contradicts the documented neutral-NULL behaviour (D17) and cannot reach the optimizer's features through NULL storage.
5. "Raising the CLIP tag threshold to the documented 22 improves tags" - refuted (D4). Also the 22 is the wrong block, not a wrong value.
6. "The 20,054 stored silhouette flags come from the current rule" - they come from an older looser rule (D12); 9,365 of them would not be set by today's code.
7. "`night` is not in the quality-cap list" - it is (9.90); the 9.40/9.60/9.90 ceilings are theoretical (no photo within 0.5).
8. "`ScoringConfig.get_clip_config()` is a safe read of the active profile" - it does not resolve `auto` (D5); used naively it gives an `auto`->16gb install a 0.22 threshold on SigLIP cosines (almost no tags).
9. "Storing NULL in the saliency no-subject branch is a two-line change" - the batch-level `lost` count at `saliency_scorer.py:541` tests `subject_sharpness is None` and would log a false "Saliency failed" error for every no-subject photo after the change.
10. "Switching the writers to NULL fixes the optimizer's 5.0 problem" - `build_metric_vector` turns NULL back into 5.0 before the optimizer sees it (D17).
11. "`detect_vram` needs its own fix" - it already routes through `is_device_available`; fixing `_cuda_is_available` fixes both (D9).
12. "`photo_tags` is stale on the library" - the copy is fully in sync (D7); the defect is latent until the next scan after a `--migrate-tags`.
13. "The strict silhouette rule leaves ~477 silhouette-category photos on the library" - that is the rescan figure (S1). A thumbnail backfill that clears unresolved rows lands near 320 (S1m).
14. "T2 keeps today's behaviour for `clip_legacy`" - true only for installs on the shipped defaults. An old full config (D25) carries `clip_legacy: 22`; making the existing key live would silently turn its 8gb/legacy effective threshold from 0.08 into 0.22. Hence the NEW key name (T2).
15. "T8 touches only the scan-time writers of the 5.0 placeholders" - `Facet.recompute_composition_scores` consumes the same function and would crash on the NULL (D27).
16. "The optimizer's current weights are the served weights" - for the ten quality categories they are not (D29); T9a's prior, the McNemar baseline and T9b's defect-5 shift were all measured in the wrong weight space, and the original T9b check ran on `portrait`, which has no `quality_percent`.
17. "Editing the shipped astro filter reaches every install" - not an install whose operator file carries a `categories` array (D26).
18. "Gallery/stats `--recompute-average` replays are evidence for T6/T8" - a recompute replays STORED rows, which still hold 5.0 after T8, so the zero-change replay holds by construction; only the explicit NULL-vs-5.0 test exercises T8.

     ```
     subject = face in face_details with the largest bbox area      # bbox = [x1,y1,x2,y2] in gray's pixel space
     ```
