## Objective + success criteria

- S1 (Step 1). A single-pass scan on a profile whose aesthetic model is TOPIQ (`16gb`, `24gb`) outside
  commercial mode logs a WARNING and runs multi-pass; `--pass NAME` and `--dry-run` are not touched by that
  preflight. Independently, no code path returns `(5.0, embedding, None, 'topiq')` or a neutral 5.0 labelled
  `clip-mlp` when `aesthetic_head is None` and the mode is not commercial: both raise `RuntimeError`, and in a
  scan the photos land in `scan_failures` and are never saved.
- S2 (Step 2). `GET /api/stats/categories/metrics` is gone from the app, from the OpenAPI schema, from
  `client/src/app/core/api/schema.d.ts` (a pure-removal diff, regenerated by `npm run gen:api`) and from the
  seven VIEWER docs; the sibling `/api/stats/categories/{breakdown,weights,correlations,overlap}` routes are
  untouched.
- S3 (Step 3). `GET /api/albums/{id}/photos?sort=top_picks_score` and the shared-album route answer 200 and
  sort by the top-picks score for smart AND regular albums, and each returned photo carries
  `top_picks_score`. Every member of `VALID_SORT_COLS` is exercised against both album kinds by one test, so a
  future computed sort alias cannot reintroduce the 500.
- S4 (Step 4). `scan_runs.failed_files` equals the number of DISTINCT `(scan_run_id, path)` rows in
  `scan_failures`, however many times a path fails and however the failures straddle flushes. A repeated
  failure keeps the FIRST stage and appends the new error text, bounded to 2000 characters. No schema change.
- S5 (Step 5). `python facet.py --recompute-iqa` no longer re-attempts (a) a photo whose stored thumbnail has a
  post-bound short side under 224 px for LIQE (skipped before any decode or forward, counted in the summary,
  nothing recorded) and (b) a photo TOPIQ NR-Face declined with "No face detected" on its CURRENT scan
  (remembered in `iqa_declined`, keyed by a fingerprint that a rescan invalidates). An OOM or any other
  unexpected failure is still retried. A decline never survives a rescan of the photo.
- S6 (Step 6). Recorded as a non-goal: no change to the TOPIQ batch-of-one OOM retry.
- S7 (Step 7). `python facet.py --repair-neutral-iqa` NULLs exactly-5.0 values in `aesthetic_iaa`,
  `face_quality_iqa` and `liqe_score` and in no other column, prints per-column counts, and tells the user to
  run `--recompute-iqa` then `--recompute-average`. It is wired like `--repair-int-columns`, is classified in
  `LIBRARY_JOB_ARGS`, and is in no migrate chain.
- S8 (all). The documentation of every behaviour change lands in the same change: `CHANGELOG.md`
  `[Unreleased]`, `CLAUDE.md`, and the seven-language docs listed in "Docs anchors". `ruff`, the full pytest
  suite (no failure outside the pre-recorded baseline), the leaf-project typechecks, `ng lint`, the client
  tests and the `gen:api` idempotence check all pass.

## Open questions / risks

### Premises the tree contradicted (or that the gaps reports got wrong)

- P1. There is no `--migrate-all`. `--upgrade-db` is the only chain (it subprocesses `--recompute-iqa`); Step 7's
  "not part of any migrate chain" is satisfied by leaving `--upgrade-db` and `DEFAULT_UPGRADE_FLAGS` alone.
- P2. CLAUDE.md says photos are written with `INSERT OR REPLACE`; the save has been an UPSERT since the
  rescan-preservation work (`_photos_upsert`). The consequence matters here: an UPSERT never cascades, so a
  side-table row for a path SURVIVES a rescan. That is why Step 5 needs a fingerprint at all.
- P3. gaps-b says a resumed run resets `ScanRun._failed`. `ScanRun` is constructed only in `ScanRun.start`
  (`scan_state.py:50-52`); a "resume" starts a NEW run id. The double count is purely within one run.
- P4. gaps-b recommended a nullable `photos` column for the decline. The locked decision is a side table, which is
  also what CLAUDE.md requires ("sticky per-photo state goes in a side table"): `photos` is rewritten on rescan.
- P5. Locked 1(a) says dry-run is "unaffected". That is true of the PREFLIGHT, but 1(b) makes `--dry-run` on a
  TOPIQ profile fail per photo, because dry-run builds an eager (non-multi-pass) `Facet` and calls the
  single-image aesthetic path. See Q1.
- P6. gaps-a says `get_aesthetic_and_quality` is reached from the scan. It is reached only by dry-run
  (`score_photo_from_pil`), which swallows and logs the exception; nothing is recorded in `scan_failures` there.
- P7. Exactly one test pins the head-less fake: `tests/test_licensing_gate.py:1107-1108`. The other two
  `aesthetic_head = None` sites (967, 1069) are commercial-mode or stub setups and keep passing.
- P8. gaps-a's claim that the 5.0 is "a TOPIQ failure" is wrong: single-pass NEVER runs TOPIQ. Every photo of a
  head-less single-pass run was stamped `scoring_model = 'topiq'` with `aesthetic = 5.0`.
- P9. `--dry-run` and the maintenance flags: `--repair-int-columns` silently ignores `--dry-run`; the precedent
  has no dry-run. Q3.
- P10. The `scan_runs.mode` label was wrong for config-driven single-pass (`'multi-pass'`). It has no reader
  (`git grep -n "scan_runs" -- '*.py'` outside schema/tests shows only the INSERT), so fixing it is a free
  by-product of Step 1, not a feature.

### Questions (each carries the default the spec uses)

- Q1. `--dry-run` on a TOPIQ profile. AMENDED (Adversarial review A1): the single-image path returns `None`
  for the aesthetic instead of raising, `_report_dry_run` prints it as `n/a`, and the aggregate is unchanged
  (NULL scores neutral 5.0, the exact value it fabricated before). Raising would have made every sample fail
  and `--dry-run` exit 1 on `16gb`/`24gb`. Rejected: routing dry-run through the multi-pass processor (a new
  feature). O1 stays as a runtime observation of the `n/a` output.
- Q2. Pre-1.20 libraries can hold a fake 5.0 in `topiq_score` and `aesthetic` as well: before #184 a failed
  primary TOPIQ stored `aesthetic = quality_score = topiq_score = 5.0` (the previous spec's S5). They are NOT in
  `--repair-neutral-iqa`: a genuine rounded 5.00 is indistinguishable, `aesthetic` is also the CLIP-MLP column on
  `legacy`/`8gb` where 5.0 is ordinary, and `--recompute-iqa` cannot refill either (only `--score-topiq`
  refills `topiq_score`; `aesthetic` needs a `--force` rescan). OPEN for the user: add an opt-in
  `--include-primary` later? DEFAULT: no, and say so in the docs and the CHANGELOG.
- Q3. `--repair-neutral-iqa --dry-run`. The precedent silently ignores `--dry-run`; a writer that ignores a
  preview flag is a trap. DEFAULT (my addition, not locked): refuse with a message and exit 1. Reversible in one
  line if the user prefers parity with `--repair-int-columns`.
- Q4. A stale decline can survive a rescan only if the rescan lands in the same second with a thumbnail of
  identical byte length. Accepted: the fingerprint is `scanned_at || '|' || length(thumbnail)`; there is no
  "clear declines" command. Any ordinary rescan (`--force`) clears it by writing a new `scanned_at`.
- Q5. The LIQE skip count is an upper bound and the model is still loaded: the up-front "N NULL" count cannot
  know a thumbnail's geometry without decoding it, so a library whose only NULL is a too-small thumbnail loads
  LIQE and header-checks every such row on every run. Accepted (a header parse is microseconds per row).
  Possible follow-up: load scorers lazily on the first non-empty batch.
- Q6. `_IQA_DECLINING_MODELS` has one entry (`face_quality_iqa` -> `topiq_nr_face`). It is a map rather than a
  constant so the selector and the writer stay symmetric if another model ever gains a deterministic decline.

  has no expected skip.
